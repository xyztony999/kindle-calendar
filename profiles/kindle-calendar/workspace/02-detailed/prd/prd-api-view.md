## 0. 需求澄清（D0）

用户原话是：给网页首页的 API 做美化页，点开不再是纯 JSON。Kindle 自己拉的 PNG 和机器接口不能被改坏。机器客户端仍拿到原来的 JSON 或 PNG；浏览器点开时看到阅读页。

首页「接口」一节现在链出 8 个地址。点进去的实际结果是：

| 首页链接 | 今天点开是什么 | 本次 |
|----------|----------------|------|
| `/api/v1/dashboard.json` | 整页 JSON | 浏览器改为阅读页；机器仍是这份 JSON |
| `/api/v1/dashboard.env` | 整页 env 文本，不是 JSON，但是同一类「点开就是机器原文」 | 浏览器改为阅读页；Kindle `dash.sh` 仍 source 这份文本 |
| `/r/<page>/<region>.png` | 图片 | 不改 |
| `/r/today/clock/<glyph>.png` | 图片 | 不改 |
| `/dashboard.png` | 图片 | 不改 |
| `/admin` | 已经是管理端页面 | 不改 |
| `/weather` | 整页 JSON | 浏览器改为阅读页；机器仍是这份 JSON |
| `/health` | 整页 JSON | 浏览器改为阅读页；首页脚本和 `curl /health` 仍是这份 JSON |

页脚「原始 JSON」指向 `/?format=json`，这是故意给人看机器清单的入口，保持 JSON。

| 维度 | 结论 |
|------|------|
| 业务术语 | 接口阅读页、机器原文、网页声明 |
| 角色 | 维护者用浏览器从首页点进数据地址。家庭用户仍在 Kindle 上看画面，本模块不给他们新菜单。部署脚本和 `dash.sh` 是机器客户端 |
| 匹配 | 部分匹配。四个地址、首页链接、PNG 和管理端都已存在。缺的是浏览器阅读呈现 |
| 类型 | 增强。不新建业务域，在双语呈现下增加 L4 |
| 状态 | 无状态机。一次请求要么是阅读页，要么是机器原文 |
| 规则 | 见第 4 节。默认偏向机器原文，只有明确要网页时才出阅读页 |
| 集成 | 阅读页只读已经组装好的载荷、env 文本和服务状态。不新接外部数据源，不改鉴权 |

本阶段按代码把范围定死，不再逐项追问。确认点放在 Gate 1。未确认前不写业务代码。

### 0.1 已锁定的决策

1. 阅读页是分块页面，不是给 JSON 上色。用户要的是能读，不是另一份格式化 JSON。
2. 分流看请求要的呈现，不看 User-Agent。首页里的 `fetch("/health")` 不声明网页，必须继续得到 JSON，否则首页状态行会坏。
3. `format=json` 的含义与首页一致：要机器原文。对 env 来说，机器原文仍是 env 文本，不是把 env 包进 JSON。
4. 阅读页的版头和页内数据使用网页语言（与首页相同：地址 `lang`、Cookie `kc_lang`、浏览器语言）。机器原文的语言仍只看地址里的 `lang`，不看 Cookie，也不看 `Accept-Language`。
5. 首页链接地址和首页文案不改。浏览器自己会声明要网页，所以点原链接就能进阅读页。
6. 不改 PNG 的字节、ETag 和 304。不改 `/admin` 与 `/admin/api/*`。不改 `GET /` 的页面和它的 JSON 清单。

## 1. 背景与目标

首页把数据地址直接放给用户点。浏览器打开后是一整页 JSON 或 env 文本，天气、日期、服务是否正常都混在结构里，看不出重点。

**为谁**：在浏览器里打开首页、再点「接口」的维护者。

**价值**：这四个地址在浏览器里变成和首页同一套纸感的阅读页；Kindle、`wget`/`curl`、首页状态脚本和管理端继续拿到今天的正文。

## 2. 范围

| 做 | 不做 |
|----|------|
| `GET /api/v1/dashboard.json`、`GET /weather`、`GET /health` 在明确要网页时返回阅读页 | 不改这三份 JSON 的字段、键名和成功时的结构 |
| `GET /api/v1/dashboard.env` 在明确要网页时返回阅读页，页内可展开与机器原文一致的文本 | 不改 env 的键、行序和可被 shell source 的正文 |
| 阅读页用中英文版头，浅色纸感，并跟随系统深色 | 不引入前端框架、CDN、外部字体或 JSON 高亮库 |
| 阅读页提供「原始数据」链接，强制回到机器原文 | 不把 `/?format=json` 的接口清单改成页面 |
| 协商响应带 `Vary: Accept` | 不改 PNG、时钟字形、整页图 |
| 打开 env 的阅读页仍计一次心跳，且只在正文成功生成之后 | 不改 `/admin` 页面，也不改 `/admin/api/*`（含导出） |
| 动态文字按页面文本写入，避免把城市名或错误句当成标记 | 不新增登录，不改口令、会话和配置存储 |

## 3. 角色

| 角色 | 本次操作 |
|------|----------|
| 维护者 | 从首页点进四个数据地址，阅读分块页面；需要原文时点「原始数据」。可用语言按钮切换中英文 |
| 家庭用户 | 无新操作。设备上的画面、翻页和轮播不变 |
| 机器客户端 | `dash.sh`、部署脚本里的 `curl /health`、首页的 `fetch("/health")`、不声明网页的请求。它们拿到的正文与今天相同 |

## 4. 规则

### 4.1 什么时候出阅读页

只对第 2 节列出的四个地址做分流。其它地址保持今天的行为。

判定顺序：

1. 查询参数 `format` 去掉空白后是 `json`（不区分大小写）→ 机器原文。此时不再看 Accept。
2. `format` 是 `html` → 阅读页。
3. `format` 是其它非空值 → 机器原文。不认识的值不当成网页。
4. 没有 `format` 时，只看 Accept 里写明的类型：
   - `text/html` 的质量高于 `application/json`，且 `text/html` 的质量大于 0 → 阅读页。
   - 没有出现的类型，质量按 0。`*/*` 不单独抬高任何一方。
   - 没有 Accept、只有 `*/*`、两者质量相等、或 JSON 更高 → 机器原文。

不使用「在两个类型里挑一个最匹配」的办法，也不看 User-Agent。浏览器地址栏会写明 `text/html` 且质量高于 JSON，因此从首页点进去是阅读页。`curl`、`wget`、Kindle 和 `fetch` 默认不写明 `text/html` 更高，因此仍是机器原文。

### 4.2 机器原文

| 地址 | 机器原文 |
|------|----------|
| `/api/v1/dashboard.json` | 现有台历 JSON。语言只看查询参数 `lang` |
| `/weather` | 现有天气 JSON：`current`、`daily`、`hourly`。语言只看 `lang` |
| `/health` | 现有健康 JSON，含 `status: ok` 以及今天已有的画面、城市、天气年龄等字段 |
| `/api/v1/dashboard.env` | 现有 env 文本，媒体类型仍是今天的 `text/plain`。语言只看 `lang`。正文成功生成后才记心跳 |

`format=json` 对 env 表示「要这份 env 文本」，不是「把 env 变成 JSON」。

成功响应若经过了分流，无论最后是阅读页还是机器原文，都加上 `Vary: Accept`，避免缓存把网页发给设备。

### 4.3 阅读页的语言

版头文案和页内数据使用同一套网页语言，顺序与首页相同：地址里的 `lang`，其次 Cookie `kc_lang`，再是浏览器语言，最后中文。

因此从英文首页点进 `/weather`（地址没带 `lang`）时，阅读页的标题和天气描述都是英文。同一地址若不带 Cookie、也不带 `lang`，机器拿到的仍是中文 JSON。

地址里明确带了 `lang` 时，阅读页与首页一样把选择写入 `kc_lang`。机器原文的响应不写这个 Cookie。

阅读页上的「原始数据」：

- 中文页：同一路径加 `format=json`。
- 英文页：同一路径加 `format=json` 和 `lang=en`，使原文和眼前这一页的语言一致。
- `/health` 没有语言数据，原始数据链接只加 `format=json`。

语言按钮与首页相同：当前中文时按钮写 English，当前英文时按钮写中文。链接只改 `lang`，不带 `format`。

### 4.4 四个阅读页要呈现的内容

字段只用该地址今天已经返回的数据，不新增 JSON 键。

**台历数据**（`/api/v1/dashboard.json`）：地点、生成时间、已启用页面、配置版本；日期与农历、干支生肖、节日；宜与忌；节气与下一节气；当前温度和天气描述；日出日落；月相沿用载荷里已有的名称；空气质量，没有则写暂无；一言正文和出处。逐时明细不在本页铺开，页内链到天气阅读页。

**天气**（`/weather`）：地点若当前载荷里有则放在标题，数据块只来自这份天气 JSON。大号当前温度与描述，湿度与风速，逐日表（日期、描述、最高、最低），逐时表（时间、温度、降水概率）。

**服务状态**（`/health`）：在线；画面尺寸；城市；配置版本；已启用页面；天气是否已更新、数据年龄、是否正在刷新。`last_error` 非空时原样显示，不翻译这句服务器文字。

**设备清单**（`/api/v1/dashboard.env`）：先给摘要：屏幕宽高、页面顺序、轮播是否开启、各页停留、触摸让位秒数、配置版本、有没有 `lang` 行、分区地址条数。后面用可展开区域放完整原文，展开后的文本与同语言的机器原文逐字相同。页上说明：打开本页会计一次拉取，和管理端看到的最近拉取是同一件事。

组装失败时（例如天气数据还没有）：JSON 与 env 的机器分支不捕获，保持今天的失败方式。阅读页分支返回一页「暂时读不到」，状态码 500，不把堆栈展示给用户，也不把失败改成一份新的 JSON。`/health` 在天气缺失时本来就是成功 JSON，阅读页同样返回 200，并写明天气暂不可用。

### 4.5 外观

浅色变量与当前首页一致：纸色背景、深色字、衬线标题、卡片。系统深色时改为深底浅字，规则与双语网页相同，不另加主题开关。页面宽度适配手机，表格可以横向滚动。页头有返回首页和语言按钮。不加载外部资源。

## 5. 验收

代码阶段用测试固定下面这些行为，不在本设计阶段改代码：

1. 四个地址在 `Accept: text/html` 时返回 HTML，正文里有给人读的标题，而不是以 `{` 开头的 JSON，env 阅读页也不是以赋值语句开头。
2. 不带 Accept、`Accept: */*`、`Accept: application/json`、`format=json` 时，三个 JSON 地址仍是 JSON，env 仍是可被 source 的文本，且不以 `<` 开头。
3. `format=json` 优先于 `Accept: text/html`。
4. `format=html` 在 `Accept: */*` 时仍是阅读页。
5. `format` 为其它值时是机器原文。
6. 英文 Cookie 下，阅读页标题为英文；不带 Cookie 的 JSON 不因为别人的网页语言而变成英文。
7. `/health` 在 `Accept: */*` 时仍能被 `response.json()` 解析，字段与现在一致。
8. PNG 与 `/admin/api/settings` 的成功响应类型不变。
9. 协商过的成功响应带 `Vary: Accept`。
10. 城市名或错误句里的 `<` 在阅读页里按文本显示，不变成标记。
